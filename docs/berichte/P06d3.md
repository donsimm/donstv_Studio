## 2. Absturz erfassen (Aufgabe 2)

- Bei Exit-Code 139, −11, 134 oder −6 druckt die Startprüfung die **ganze** Ausgabe von `faulthandler` (ab «Fatal Python error», alle Threads, Zeilen mit `#`) und schreibt `startpruefung-absturz-<Variante>-<Lauf>.txt` in den Ordner des Repos (`--ausgabe` ändert den Ordner): Vorbereitung, ganzes stderr, C++-Aufrufliste.
- C++-Aufrufliste: Ist `gdb` vorhanden, erlaubt die Prüfung Core-Dateien für ihre Kindprozesse (`RLIMIT_CORE` auf die harte Grenze, vererbt; kein `preexec_fn`) und ruft `gdb -batch -ex "thread apply all bt 60"` auf eine Core-Datei im Ordner des Laufs auf, sonst über `coredumpctl debug` (falls `core_pattern` an systemd-coredump geht). Sonst steht dort, warum es keine gibt.
- Geprüft mit einem künstlichen Speicherzugriffsfehler (Test `test_f01_crash_is_recorded_with_full_traceback`): Exit-Code −11, ganze Aufrufliste mit dem Hauptthread in `ui/main.py` (`app.exec()`), Datei geschrieben. **Im Container entsteht keine Core-Datei**, sobald QtWebEngine geladen ist (ein reiner Python-Prozess schreibt eine); die Datei meldet dann «keine Core-Datei gefunden (core_pattern: core)». Auf dem Laptop gab es laut Befund eine (168 MB); ob `gdb` dort automatisch greift, ist nicht gemessen.
- Bei einem Absturz ist der Exit-Code des Kindprozesses −11 (Signal), nicht 139; 139 meldet nur eine Shell. Beides gilt als Absturz.

## 4. Ursache im Code (Aufgabe 4)

Gelesen: `git diff 6dc8f44..54f6696 -- src/donstv_studio/ui` (11 Dateien, 722 Zeilen hinzu, 71 entfernt) mit der Frage, was beim Eintreffen der ersten Datenantwort geschieht.

Ablauf (Code, Stand `54f6696`): `CoreLink` verbindet → `EditorModel.load` im Hintergrund-Thread → Ergebnis über das Signal `_wake` an `TaskRunner._drain` im Hauptthread → `EditorModel._loaded` → `overlays_changed` → `OverlaysDock.refresh`: `list.clear()`, 3 Einträge, `_sync_current(None)` (`setCurrentRow(-1)`, `_updating` gesetzt), `stack.sync()` → `setCurrentWidget(listing)`. Danach erst `select_overlay` (Quellen, Eigenschaften, Vorschau mit QtWebEngine). Der Absturz liegt laut Aufrufliste **vor** `select_overlay`; zu diesem Zeitpunkt hat keine Quelle ein Widget.

Was `setCurrentWidget` tut (Qt 6.8.2, Quelltext, siehe `docs/02-architektur.md`): alte Seite `clearFocus` und `hide`, neue Seite `raise` und `show`; `show` poliert die Liste (Stylesheet) und aktiviert die Layouts aller sichtbaren Eltern bis zum Hauptfenster (`QMainWindowLayout`, Dock-Bereiche, Kopf, Statuszeile). Dabei laufen Python-Handler (`resizeEvent` von `EditorView` und `PreviewArea`), die aber zum Zeitpunkt des Absturzes nicht auf dem Stapel stehen (oberster Rahmen ist `sync`).

## Auf dem Laptop prüfen

Im Terminal **der grafischen Sitzung** (nicht über ssh), im Ordner des Repos. `donstv-core` darf laufen; die Prüfung startet eigene Kerne in leeren Ordnern und liest deine Daten bei `kopie` nur.

1. Stand holen:
   ```bash
   git fetch origin claude/epic-faraday-4rfiwx && git checkout claude/epic-faraday-4rfiwx && git pull
   ```
2. Kurzprüfung mit Daten (etwa 3 Minuten):
   ```bash
   tools/laptop_pruefung.sh kurz
   ```
   Erwartet: jeweils «5 von 5 Läufen mit Exit-Code 0» für Beenden, `standard`, `daten`, `daten_schmal`. Ohne die Zeilen zu `daten` ist das Ergebnis nicht aussagekräftig. Stürzt `daten` ab, ist das der Reproduzierer; die Aufrufliste steht dann in `startpruefung-absturz-daten-<Lauf>.txt`.
3. Eingrenzen mit einer Kopie deiner echten Daten (etwa 15 Minuten; deine Daten werden nicht verändert):
   ```bash
   tools/laptop_pruefung.sh eingrenzen
   ```
   Am Ende steht «Zusammenfassung (Variante: Läufe mit Exit-Code 0)» mit einer Zeile je Variante und Schalter. Danach `laptop-ergebnis.txt` und, falls vorhanden, die Dateien `startpruefung-absturz-*.txt` im Chat anhängen.
4. Handtest mit deinen echten Daten, dreimal: `donstv-core` starten, dann
   ```bash
   python -X faulthandler -c "from donstv_studio.ui.main import main; main()"
   ```
   Fenster geht auf und bleibt offen; zu einem anderen Programm wechseln und zurück; mit dem X schliessen; Exit-Code mit `echo $?` (erwartet 0, bekannt ist 139). Bei 139 die Ausgabe von faulthandler im Chat anhängen.
5. Nur falls Schritt 3 einen Schalter zeigt, mit dem kein Absturz mehr auftritt: denselben Schalter im Handtest bestätigen, z. B.
   ```bash
   DONSTV_OFF=theme_changes python -X faulthandler -c "from donstv_studio.ui.main import main; main()"
   ```
